## 🔬 Gate-Level Simulation (GLS)

**Gate-Level Simulation (GLS)** is used to verify the synthesized gate-level netlist using a testbench.

The basic flow is:

```text
RTL Design + Testbench
        ↓
   RTL Simulation
        ↓
      Synthesis
        ↓
 Gate-Level Netlist
        ↓
 Gate-Level Simulation
```

GLS helps to:

* Verify the functionality of the synthesized circuit.
* Ensure synthesis preserves the intended behavior.
* Detect synthesis-simulation mismatches.
* Validate the gate-level implementation.
* Perform timing verification when delay information is available. 

## 📝 RTL vs. Gate-Level Netlist

**RTL** describes the intended hardware behavior using constructs such as `always`, `assign`, `if-else`, `case`, and operators.

After synthesis, the RTL is converted into a **gate-level netlist** consisting of logic gates or technology-specific standard cells.

```text
RTL Description
      ↓
   Synthesis
      ↓
Gate-Level Netlist
```

The netlist represents the actual hardware implementation generated by the synthesis tool. 

## ⚠️ Synthesis-Simulation Mismatch

A **synthesis-simulation mismatch** occurs when the behavior observed during RTL simulation differs from the behavior of the synthesized hardware.

```text
RTL Simulation
      ≠
Gate-Level Simulation
```

Common causes include:

* Incomplete sensitivity lists
* Improper use of blocking assignments
* Improper use of non-blocking assignments
* Incorrect sequential-logic coding
* RTL constructs that do not accurately represent the intended hardware 

## 🔄 Incomplete Sensitivity Lists

For combinational logic, all signals that affect the output must be included in the sensitivity list.

For example:

```verilog
always @(sel)
begin
    if (sel)
        y = i1;
    else
        y = i0;
end
```

This is incomplete because the output depends on `sel`, `i0`, and `i1`.

The preferred approach is:

```verilog
always @(*)
begin
    if (sel)
        y = i1;
    else
        y = i0;
end
```

`always @(*)` automatically includes the signals used by the combinational block. 

## 🔧 Blocking Assignment

The blocking assignment operator is:

```verilog
=
```

Blocking assignments execute **immediately and sequentially**.

They are generally used for:

* Combinational logic
* Intermediate calculations
* Procedural combinational descriptions

Example:

```verilog
q0 = d;
q  = q0;
```

The second statement can observe the value assigned by the first statement. 

## ⚡ Non-Blocking Assignment

The non-blocking assignment operator is:

```verilog
<=
```

With non-blocking assignments, right-hand-side values are evaluated first and the updates are scheduled to occur afterward.

Example:

```verilog
q0 <= d;
q  <= q0;
```

This is appropriate for **sequential and clocked logic**, as it correctly models parallel register updates. 

## ⚖️ Blocking vs. Non-Blocking

| Blocking `=`                          | Non-Blocking `<=`                         |
| ------------------------------------- | ----------------------------------------- |
| Executes immediately                  | Update is scheduled                       |
| Procedural order affects the result   | Represents parallel register updates      |
| Commonly used for combinational logic | Commonly used for sequential logic        |
| Can cause issues in clocked logic     | Preferred for flip-flop/register modeling |

### General Rule

```text
Combinational Logic → Blocking (=)

Sequential Logic → Non-Blocking (<=)
```



## 🏗️ Correct Sequential Coding

For two cascaded flip-flops, the preferred coding style is:

```verilog
always @(posedge clk)
begin
    q0 <= d;
    q  <= q0;
end
```

This correctly represents:

```text
d → FF(q0) → FF(q)
```

The use of non-blocking assignments ensures that `q` receives the **previous value of `q0`**, matching the behavior of actual sequential hardware. 

## 🔀 Ternary Operator MUX

A 2:1 MUX can be implemented using the ternary operator:

```verilog
assign y = sel ? i1 : i0;
```

The behavior is:

```text
sel = 0 → y = i0
sel = 1 → y = i1
```

This is equivalent to the procedural `if-else` implementation of the MUX.

Verilog Design
      +

      ↓
Icarus Verilog

## ⚙️ Yosys Synthesis

Yosys was used to synthesize the RTL and generate a gate-level netlist.

Typical commands include:

```text
read_verilog <design>.v
synth -top <top_module>
abc -liberty <library>.lib
write_verilog -noattr <netlist>.v
show
```

The synthesized netlist can then be used for gate-level simulation. 

## ⏱️ Functional GLS vs. Timing GLS

### Functional GLS

Functional GLS verifies the logical behavior of the synthesized netlist.

```text
Gate-Level Netlist
        +
    Testbench
        ↓
 Functional GLS
```

### Timing GLS

Timing GLS additionally considers delay information.

```text
Gate-Level Netlist
        +
Delay Information
        +
    Testbench
        ↓
   Timing GLS
```

Timing-aware GLS requires appropriate delay-annotated gate-level models.
